ComfyFleet cu124 instance pins (primary tag comfyfleet:cu124)

Host driver: CUDA 12.4. The container does not ship the driver.
Shared memory: the manager passes --shm-size 8g on every create
(Compose form: shm_size: '8g'), same as the cu130 line.
Optional alias: comfyfleet:phase1 is the same image when publish retags it.
A floating tag does not move an install that pins a digest.
Changing CUDA line is a recreate (stop, create --force, start).
start or restart alone does not replace layers.

Base
  debian:bookworm-slim
  CUDA runtime: cuda-libraries-12-4=12.4.1-1 and cuda-cudart-12-4=12.4.127-1
    from https://developer.download.nvidia.com/compute/cuda/repos/debian12/x86_64/
  cuDNN runtime: libcudnn9-cuda-12=9.1.0.70-1 (NVIDIA package description: CUDA 12.4)
  Host C compiler for Triton JIT (not the CUDA devel toolkit):
    gcc and python3-dev from Debian bookworm.
    torch 2.6.0+cu124 depends on triton==3.2.0. import comfy_kitchen loads
    backends.triton, and quantization.py's @triton.autotune initializes the
    NVIDIA driver. That compiles driver.c (cuda_utils) and needs gcc plus
    Python.h. Without gcc, triton/runtime/build.py raises
    "Failed to find C compiler. Please specify via CC environment variable."
    cuda.h ships in
    the triton wheel. g++, build-essential, and cuda-nvcc are not installed.

PyTorch (matches CUDA 12.4; not the PyPI default, which is CUDA 13)
  index: https://download.pytorch.org/whl/cu124
  torch==2.6.0+cu124
  torchvision==0.21.0+cu124
  torchaudio==2.6.0+cu124
  image Python: Debian bookworm CPython 3.11
  wheels: torch-2.6.0+cu124-cp311-cp311-linux_x86_64.whl
          torchvision-0.21.0+cu124-cp311-cp311-linux_x86_64.whl
          torchaudio-2.6.0+cu124-cp311-cp311-linux_x86_64.whl
  The torchaudio wheel's Requires-Dist is torch==2.6.0. The installed
  2.6.0+cu124 satisfies that specifier (the local version is ignored when
  the specifier has none). Manager's torch_torchvision_torchaudio_version_map
  pairs torch 2.6.0 with torchvision 0.21.0 and torchaudio 2.6.0.
  ComfyUI-Manager 14b5aaab does not import torch and does not run `pip show`.
  After `python -m pip install <package>` (the EXECUTE line, including
  cryptography; that commit does not pass -U or -c) PIPFixer.fix_broken in
  glob/manager_util.py reads the `pip list` snapshot taken before the
  command. It logs "[ComfyUI-Manager] PyTorch is not installed" when torch,
  torchvision, or torchaudio is absent from that map. Installing
  cryptography does not remove torch; it only runs the helper. Shipping
  torch and torchvision without torchaudio made every Manager pip install
  log that error while torch 2.6.0+cu124 was already in /opt/venv.
  PIP_CONSTRAINT points at /opt/comfyfleet/torch-constraints.txt, which
  lists these three wheels and numpy==2.2.6, so a later Manager install
  cannot replace them. docker/verify_image_pins.py parses `pip list` the
  same way and fails the build if any of the three is missing or not the
  cu124 pin. No GPU. An existing container keeps the old image until it is
  stopped and replaced with create --force.

ComfyUI-Manager

  That commit reads <user>/__manager/config.ini. ComfyUI v0.38.0 has
  get_system_user_directory, and the entrypoint does not pass
  --user-directory, so the file is /opt/ComfyUI/user/__manager/config.ini.
  A missing file leaves allow_git_url_install and allow_pip_install false.
  docker/seed_manager_config.py (from the entrypoint, every start) sets
  allow_git_url_install=true, allow_pip_install=true, security_level=normal
  in [default] without dropping other keys.
  is_dedicated_install_allowed in that commit is flag AND loopback listen.
  --listen stays 0.0.0.0 so Docker can publish the port onto the docker.sock
  LAN. docker/patch_manager_trusted_install.py (late image layer, after the
  torch and clone layers) keeps the flag and skips the loopback term when
  COMFYFLEET_TRUSTED_INSTALL=1, which the entrypoint exports. Unset, the
  stock check remains. A Manager on the public internet is a different
  threat model; the env var is the gate for this image.

numpy
  numpy==2.2.6
  Installed from PyPI before ComfyUI and custom-node requirements, then
  written into /opt/comfyfleet/torch-constraints.txt with the torch pins.
  PIP_CONSTRAINT points at that file. Manager's installer inherits it, so
  those installs cannot replace numpy (or the CUDA 12.4 torch wheels).
  ComfyUI v0.38.0 asks for numpy>=1.25.0. RES4LYF asks for numpy>=1.26.4.
  opencv-python 5 asks for numpy>=2. 2.2.6 satisfies all three.
  docker/verify_image_pins.py asserts the version during the image build.

OpenCV shared libraries (Debian bookworm apt, not version-pinned)
  libxcb1        libxcb.so.1
  libx11-6       libX11.so.6
  libxext6       libXext.so.6
  libice6        libICE.so.6
  libsm6         libSM.so.6
  libglib2.0-0   libglib-2.0.so.0 and libgthread-2.0.so.0
  libgl1         libGL.so.1
  RES4LYF images.py imports cv2 at custom-node load. opencv-python is not
  the headless distribution; requirements.txt names opencv-python, and pip
  would still install that wheel if a headless build were substituted.
  The wheel pip selects for CPython 3.11 on bookworm today is
  opencv-python 5.0.0.93 manylinux_2_28. Its cv2 extension loads bundled Qt,
  which needs libGL.so.1 and libglib-2.0.so.0 at import. The Qt xcb platform
  plugin libqxcb.so is linked directly to libxcb.so.1 (the crash on
  bookworm-slim), plus libX11, libXext, libSM, and libICE.
  matplotlib's Agg backend and the PyWavelets 3.11 wheel do not add system
  libraries beyond glibc and libstdc++ (already present via gcc).
  The image build runs docker/verify_image_pins.py, which imports cv2 and
  dlopens libxcb.so.1 and libqxcb.so. No display and no GPU.

comfy-kitchen
  0.2.36 pure-Python wheel (eager backend): comfy_kitchen-0.2.36-py3-none-any.whl
  https://files.pythonhosted.org/packages/38/23/a6787aac01d7c28ae3cb07579ba839297a35e6fad66baac096916246cc7f/comfy_kitchen-0.2.36-py3-none-any.whl
  The manylinux wheel targets CUDA 13 and is intentionally not installed.
  torch 2.6.0+cu124 infer_schema rejects PEP 585 list[int] and list[bool] on
  custom ops (first crash: backends/eager/conv3d.py parameter stride). There is
  no stable torch>=2.7 cu124 wheel, so torch stays 2.6.0+cu124. After install,
  docker/patch_comfy_kitchen_torch26.py rewrites those custom-op annotations
  to typing.List, then imports the patched eager modules so torch 2.6
  infer_schema registers them. The image build does not import the top-level
  comfy_kitchen package. That import loads the Triton backend, and Triton
  raises "0 active drivers" when the build has no NVIDIA driver. A GPU host
  gets past that check and JIT-compiles cuda_utils; gcc and python3-dev in
  the base packages are what that compile uses. The link is -lcuda against
  the host driver mounted into the container (libcuda.so).
